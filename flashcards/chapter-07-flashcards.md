## Chapter 7: Microservice Security III: Runtime Sandboxes (gVisor & Kata) — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What Kubernetes API object maps a pod to a specific low-level container runtime? | RuntimeClass (node.k8s.io/v1). Exam tip: the 'handler' field must match the runtime name configured in the node's container runtime (e.g., containerd). |
| 2 | Which pod spec field assigns a RuntimeClass to a pod? | spec.runtimeClassName. Exam tip: it must match the metadata.name of an existing RuntimeClass object — not the handler field. |
| 3 | What does the RuntimeClass 'handler' field do? | Maps the RuntimeClass object to the runtime name registered in the CRI (e.g., a runtimes.<handler> entry in containerd's config.toml). Exam tip: a mismatch here is a common cause of pod creation failure. |
| 4 | How do you verify which runtime a running pod actually uses? | Check the pod's spec.runtimeClassName and cross-reference the node's CRI configuration for that handler. Exam tip: there is no per-pod 'runtime status' field — verification is spec + node config. |
| 5 | What is gVisor's core isolation mechanism? | Sentry — a user-space application kernel that intercepts and implements the container's syscalls instead of passing them to the host kernel. Exam tip: reduces host kernel attack surface without full virtualization. |
| 6 | What is Kata Containers' core isolation mechanism? | Each pod runs inside a lightweight VM (via a hypervisor such as QEMU/KVM) with its own guest kernel. Exam tip: strongest isolation of the two sandbox runtimes because the host kernel is never shared. |
| 7 | What does spec.overhead on a RuntimeClass represent? | The additional CPU/memory resources the runtime itself consumes (e.g., VM overhead for Kata), used by the scheduler in addition to the pod's own requests/limits. Exam tip: mainly relevant for VM-based runtimes. |
| 8 | What is the primary use case for assigning a gVisor/Kata RuntimeClass? | Isolating untrusted or multi-tenant workloads (e.g., third-party/unknown container images) to limit the blast radius of a container escape. Exam tip: pair with dedicated node pools for sandboxed workloads. |
| 9 | gVisor vs Kata: which shares the host kernel? | gVisor intercepts syscalls in user space but still runs on a shared execution environment; Kata gives each pod a completely separate guest kernel. Exam tip: Kata = stronger isolation, higher overhead. |
| 10 | When should you avoid gVisor or Kata and use plain runc instead? | For trusted, performance-sensitive, syscall-heavy workloads (e.g., databases) — sandbox overhead reduces throughput. Exam tip: default to runc for trusted internal workloads. |
| 11 | What is a common compatibility trap with gVisor? | Not every syscall is fully implemented/emulated by Sentry, so some specialized workloads may behave differently or fail under gVisor. Exam tip: test compatibility before mandating gVisor cluster-wide. |
| 12 | Why doesn't seccomp or NetworkPolicy replace gVisor/Kata for untrusted workloads? | Seccomp filters syscalls on a shared host kernel; NetworkPolicy governs network traffic — neither adds a boundary between the container and the host kernel itself, which is what gVisor/Kata provide. Exam tip: combine seccomp with RuntimeClass sandboxing; they address different threats. |
