## Chapter 2: Cluster Hardening I: RBAC Least Privilege & Service Accounts — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Role vs ClusterRole — scope difference? | Role = namespace-scoped, permissions apply only within its own namespace. ClusterRole = cluster-scoped, can apply cluster-wide OR be bound within a single namespace via RoleBinding. Exam tip: a ClusterRole+RoleBinding pairing is a valid pattern for reusing one role definition across many namespaces. |
| 2 | RoleBinding vs ClusterRoleBinding — what can each reference? | RoleBinding can reference either a Role OR a ClusterRole (scoped to its own namespace either way). ClusterRoleBinding can ONLY reference a ClusterRole and grants access across the entire cluster. |
| 3 | Command to test if a ServiceAccount can perform an action? | kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<namespace>:<sa-name> -n <namespace>. Must use full 'system:serviceaccount:ns:name' identity string, not just the SA name. |
| 4 | Command to list ALL permissions a user/SA currently has? | kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa> -n <ns>. Shows every verb/resource combination granted — useful for RBAC audits. |
| 5 | Which PodSpec/ServiceAccount field disables auto-mounting the SA token? | automountServiceAccountToken: false. Can be set on the ServiceAccount object (default for all its pods) or overridden per-Pod at spec.automountServiceAccountToken. Pod-level setting takes precedence over the ServiceAccount-level setting. |
| 6 | Imperative command to create a namespace-scoped Role? | kubectl create role <name> --verb=get,list,watch --resource=pods -n <namespace> |
| 7 | Imperative command to bind a Role to a ServiceAccount? | kubectl create rolebinding <name> --role=<role-name> --serviceaccount=<namespace>:<sa-name> -n <namespace> |
| 8 | Why are wildcard verbs/resources ("*") a CKS red flag? | Wildcards grant unintended broad access (e.g. verbs:["*"] includes delete/create/patch even if only read access was intended). Exam tip: always audit Roles/ClusterRoles for '*' in apiGroups, resources, or verbs — it's a top hardening finding. |
| 9 | What is an Aggregated ClusterRole and how is it built? | A ClusterRole with an 'aggregationRule.clusterRoleSelectors' field (label selector). The ClusterRoleAggregation controller automatically merges rules from all ClusterRoles matching those labels into this role's .rules — used to extend built-in roles like edit/view. |
| 10 | Default value of automountServiceAccountToken if unset? | true — tokens are auto-mounted by default on both the 'default' ServiceAccount and any custom ServiceAccount unless explicitly set to false at the SA or Pod level. |
| 11 | Bound ServiceAccount token (TokenRequest API) default expiration? | ~1 hour (3600s, kubelet requests slightly extended validity ~3607s) for tokens auto-mounted via projected volume; kubelet automatically refreshes the token before expiry so pods rarely notice — exam tests that these are time-bound, unlike legacy long-lived Secret-based SA tokens. |
| 12 | Least-privilege pattern for a namespace-only workload identity? | Dedicated ServiceAccount (not 'default') + Role scoped to only needed verbs/resources + RoleBinding in that namespace + automountServiceAccountToken:false unless API access is actually required. |
